# ADR-009 — Disable `react-hooks/immutability` Project-Wide

# Context

Upgrading to Expo SDK 57 pulled in `eslint-plugin-react-hooks@7`, whose `recommended` preset (consumed via `eslint-config-expo/flat`) adds a new "React Compiler" rule set: `react-hooks/immutability`, `react-hooks/refs`, `react-hooks/set-state-in-effect`, and others. These rules assume components and hook arguments are only ever read, never mutated in place — a real constraint under React Compiler's memoization model.

`react-hooks/immutability` flagged 19 call sites, all of them `sharedValue.value = ...` — Reanimated's own, documented API for driving animations from the UI thread. A `SharedValue` is deliberately a mutable container that lives outside React's render cycle; writing to `.value` is not a React state mutation the compiler needs to protect against, it's how every spring, gesture, and worklet in this app (`CLAUDE.md`'s Design section: "springs, not fixed curves, for anything the user touches") already works, and has always worked correctly. The plugin has no built-in awareness of Reanimated's `SharedValue` type, so it cannot distinguish this from an actual unsafe mutation.

# Decision

Set `react-hooks/immutability: "off"` in `eslint.config.js`, project-wide, rather than suppressing it line by line at each of the 19 (and growing) call sites.

The other new rules in the same set (`react-hooks/refs`, `react-hooks/set-state-in-effect`) stayed **on** — they caught two real bugs during the SDK upgrade (`useRetainedValue` reading/writing a ref during render in `core/ui/use-modal-progress.ts`; several components deriving state from a prop inside an effect instead of during render or an event handler) and are kept enabled deliberately.

# Alternatives Considered

- **`eslint-disable-next-line` at each of the 19 sites** — rejected: every future animated component built with Reanimated (which is this app's only animation library, per the Design section) would hit the same false positive, turning a one-time config decision into an ongoing per-line tax with no corresponding safety benefit.
- **A custom ESLint rule or type-based exemption recognizing `SharedValue`** — rejected as disproportionate; no such rule ships with `eslint-plugin-react-hooks` or `react-native-reanimated` today, and hand-rolling one is a maintenance burden for a single-project workaround.
- **Downgrading `eslint-plugin-react-hooks`** — rejected: it's a transitive dependency of `eslint-config-expo`, pinned to the SDK; fighting that pin would drift the project away from Expo's own supported lint config for no benefit, since the other new rules are worth keeping.

---

# Consequences

**Positive:**

- No behavior change — Reanimated code is unaffected; this only changes what ESLint checks.
- `react-hooks/refs` and `react-hooks/set-state-in-effect` remain enforced and already paid for themselves once (see Context).

**Negative / Trade-offs:**

- A genuine prop/hook-argument mutation bug in a non-Reanimated object would no longer be caught by this specific rule anywhere in the codebase, not just in Reanimated code. Accepted: this project's few non-Reanimated mutation risks are already covered by `strict` TypeScript and the domain-layer's pure-function discipline (`CLAUDE.md` rule 4).
