# ADR-004 — No Remote Telemetry, Analytics, or Crash Reporting in V1

# Context

Most production mobile apps integrate a third-party analytics and/or crash-reporting SDK (e.g. for usage funnels, remote error aggregation) by default. This app's Charter commits to Privacy by Default and treats accounts/backends as non-goals; `requirements/Non-Functional-Requirements.md` (NFR-8.1) already anticipates this by requiring any future remote logging to go through a dedicated ADR. This decision formally closes that question for V1: no such integration ships.

---

# Decision

V1 ships with **no remote analytics SDK and no remote crash-reporting SDK**. Production health is monitored exclusively through store-native signals (App Store Connect / Play Console crash reports, store reviews) as detailed in `reviews/Production-Checklist.md`. On-device logging (`standards/Logging.md`) never transmits data anywhere.

---

# Alternatives Considered

- **Integrate a standard crash-reporting SDK (e.g. a Sentry-like service)** — rejected for V1: even crash-only telemetry typically transmits device/session metadata off-device, which is a data flow this app's Privacy by Default principle and NFR-4 explicitly guard against without an explicit, separate decision to accept that trade-off. Revisiting this remains possible but requires updating NFR-8 and this ADR together, not a quiet library addition.
- **Integrate a usage-analytics SDK for product decisions (funnels, retention)** — rejected: directly conflicts with "no data leaves the device without explicit user action" (NFR-4.1) and isn't required to validate V1, since success metrics (`requirements/01-PRD.md`) are qualitative and can be assessed via store reviews and direct user feedback initially.
- **Build a fully custom, on-device-only crash log the user can voluntarily email in** — considered as a lighter-weight compromise; not adopted for V1 due to limited expected value versus the store-native crash reports already available for free, but remains a low-risk future candidate that would not require revisiting this ADR's core no-remote-transmission stance.

---

# Consequences

**Positive:**

- No third-party data processor to vet, disclose, or maintain a privacy policy section for — simplifies store privacy disclosures (`reviews/Release-Checklist.md`).
- Fully consistent with the Charter's Privacy by Default principle with zero exceptions to explain to users.
- Removes an entire class of dependency/maintenance burden and potential supply-chain risk (`standards/Security.md`).

**Negative / Trade-offs:**

- Less visibility into real-world crash frequency and root cause detail than a dedicated crash-reporting service would provide — the team relies on store-level crash summaries, which are typically less detailed (no stack traces in most cases) and on user-submitted reports.
- Diagnosing a hard-to-reproduce production bug may take longer without remote breadcrumbs/session context.
- Any future reconsideration of this decision (e.g. if crash-diagnosis difficulty becomes a real blocker) requires an explicit new ADR and an NFR-8 update — this is intentional friction, not an oversight.
