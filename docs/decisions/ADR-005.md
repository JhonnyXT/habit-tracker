# ADR-005 — Reminders as a Domain Port, Scheduled with Android Exact Alarms

# Context

FR-6 requires per-habit local reminders that deep-link into the app, request permission only at the moment the user enables one, and degrade gracefully when permission is denied. The `reminders` table and the `Reminder` entity existed from the first migration, but nothing persisted or scheduled anything: the reminder switch in the habit form was decorative — `onSave` wrote only name, icon, color and schedule.

Two questions had to be settled before implementing: where a platform service like notification scheduling belongs in a Clean Architecture that forbids the domain from importing platform code, and whether Android reminders should fire at the exact minute or accept the system's battery-saving batching.

---

# Decision

**1. Notification scheduling enters the domain as a port.** `NotificationScheduler` is an interface in `features/reminders/domain/`, implemented by `ExpoNotificationScheduler` in `features/reminders/data/`, and bound in `core/di`. It sits beside `ReminderRepository` and obeys the same rule: the interface lives in Domain, the platform implementation in Data. Use cases depend on the interface only, so permission handling and scheduling are domain decisions expressed in domain language, not screen logic.

**2. One reminder per habit, scheduled by the habit's own schedule.** A daily habit gets one `DAILY` trigger; a weekday habit gets one `WEEKLY` trigger per selected day, with identifiers derived from the reminder id (`<reminderId>#<weekday>`) so cancellation stays exact. Editing a habit reschedules with the new name and days; archiving cancels; deleting removes row and notification. `syncReminders` re-schedules everything from SQLite on each launch, so the OS and the database can never disagree for long.

> **Superseded in part by `decisions/ADR-008.md` (2026-08-05):** a habit may now have up to three reminders (`kind: 'main' | 'pre' | 'followup'`), restricted to daily-schedule habits. The scheduling mechanics described here (one `NotificationScheduler.schedule` call per enabled reminder row) are unchanged — ADR-008 only changes how many rows a habit may have and where that count is capped.

**3. The app declares `SCHEDULE_EXACT_ALARM`.** `expo-notifications` calls `setExactAndAllowWhileIdle` when `canScheduleExactAlarms()` is true and falls back to the inexact `setAndAllowWhileIdle` otherwise. Without the permission, a reminder set for 11:54 was observed arriving at 11:56 on a real device, because Android batches inexact alarms. Declaring the permission moves scheduling onto the exact path.

**4. No dedicated UI for the exact-alarm permission.** Settings exposes a single "Permiso" row that requests notification permission when it has never been asked and otherwise opens the app's page in system settings, where both "Notifications" and "Alarms & reminders" live. A separate in-app row for exact alarms was built and then removed as unnecessary surface area.

---

# Alternatives Considered

- **Put `expo-notifications` calls directly in the screens** — rejected: it would spread platform knowledge across `habit-form.tsx` and `settings.tsx`, and make "request permission exactly when the switch is turned on" a rule enforced by convention rather than by a use case.
- **`USE_EXACT_ALARM` instead of `SCHEDULE_EXACT_ALARM`** — rejected: it is granted at install with no user interaction, but Google Play restricts it to apps whose core function is alarms, timers or calendars. A habit tracker very likely does not qualify, so shipping it trades a small UX win for a plausible store rejection.
- **Accept inexact alarms** — considered seriously and rejected only because the drift is unbounded in principle: a couple of minutes when the phone is awake, potentially much longer when it has been idle. A reminder that may or may not arrive near its time undermines the feature's only promise.
- **A dedicated "Alarmas exactas" row in Settings** — implemented, then removed. It made the permission discoverable, but added a second notification-related row whose state could not be read from JavaScript (Android exposes no API for `canScheduleExactAlarms` to React Native), so it would have shown an action without a state next to a row that shows its state.

---

# Consequences

**Positive:**

- The domain owns the reminder rules; `features/reminders/` is understandable and removable on its own, per `02-Architecture.md`'s feature-first goal.
- Reminders survive reinstalls and reboots as far as SQLite is concerned, because `syncReminders` rebuilds OS state from the database rather than trusting it.
- With the permission granted, a reminder fires at its minute instead of within a battery-saver window. **Measured on a Samsung SM-S928B (Android 16):** without the permission, a reminder set for 11:54 was delivered at 11:56, and `dumpsys alarm` reported `window=+2m1s668ms`. With it granted, the same alarm reported `window=0 exactAllowReason=permission` with `whenElapsed == maxWhenElapsed`, and the notification posted 94 ms after its scheduled instant.

**Negative / Trade-offs:**

- `SCHEDULE_EXACT_ALARM` is a Play Console "sensitive permission": publishing requires a declaration explaining why the app needs it. This is a release-time cost, recorded here so it is not discovered late.
- On Android 13+ the permission is denied by default and the user must enable it in system settings. With the dedicated row removed, nothing in the app points there, so most users will run with inexact alarms unless they find the toggle themselves. Revisit if reminder timing turns out to matter to real users.
- The permission required regenerating the native project (`expo prebuild`) and reinstalling the APK — JS-only reloads cannot pick it up.
