# Context

`01-PRD.md` describes first launch as "onboarding explains the philosophy in a few screens", and `User-Journeys.md` Journey 1 adds two constraints the PRD line does not: no permission requests during onboarding, and a success condition of "a usable Today screen with at least one habit in under a minute, without being forced through screens irrelevant to that goal".

The Charter pulls in the same direction from a different angle: *Clarity Over Complexity* states plainly that "users should never need tutorials", and *Less, but Better* rejects anything that does not improve the daily experience. A three-page swipeable carousel is the default shape for onboarding, and it is exactly what those two principles argue against.

Separately, the screen needs a first-launch gate, which means the app has to decide between two entry points before the first frame is drawn.

---

# Decision

**1. One screen, not a carousel.** The three principles — private by design, consistency made visible, start small — are a short vertical list on a single screen. The primary action is "Crear mi primer hábito", which marks onboarding seen and opens the habit form. A quiet secondary action ("Lo haré después") goes straight to Today. No paging, no dots, no "next" chain.

**2. The flag lives in SQLite, not in a separate store.** Migration 2 adds a `preferences(key, value)` table behind a `PreferencesRepository` port. The app already owns a database; adding an async-storage dependency for one boolean would be a second source of truth for user state, and "delete all data" would then have two places to clear.

**3. Routing is declarative, via `Stack.Protected`.** The root layout reads the flag, puts it in a small store, and guards the two branches: `onboarding` when pending, `(tabs)` + its pushed screens when not. Flipping the flag moves the user; nothing calls `router.replace` at startup.

**4. The "create my first habit" intent travels through the store, not the navigator.** Completing onboarding sets `wantsFirstHabit`; the Today screen consumes it on its first focus and opens the form.

---

# Alternatives Considered

- **A three-page carousel** — rejected against the Charter, as above. It also costs the user three taps before reaching any value, against Journey 1's success condition.
- **`router.replace('/onboarding')` from the root layout effect** — implemented first, and it produced a **render loop**: the layout re-rendered roughly fourteen times per second and the app showed a black screen. Redirecting imperatively while the navigator is still mounting fights the router. `Stack.Protected` expresses the same intent declaratively and fixed it outright.
- **`router.push('/habit-form')` straight from the onboarding screen** — implemented first, and it silently did nothing: at the moment of the push, `habit-form` still sat behind a guard that was false, so the navigation was dropped. Hence decision 4.
- **`expo-secure-store` or async storage for the flag** — rejected per decision 2.
- **Asking for notification permission during onboarding** — explicitly rejected by Journey 1; permission is still requested only when a reminder switch is turned on (FR-6.2, `ADR-005.md`).

---

# Consequences

**Positive:**

- First launch reaches a usable Today screen in one tap, or two if the user creates a habit — comfortably inside Journey 1's minute.
- No startup redirect race, and no imperative navigation at boot to reason about.
- The flag is inside the same database as everything else, so "delete all data" and any future export/import see it without special cases.

**Negative / Trade-offs:**

- One screen carries all three principles, so the copy has to stay short. Adding a fourth idea later means either cutting one or reconsidering this decision, not quietly appending a paragraph.
- `Stack.Protected` decides *availability*, not *navigation*: both branches must be guarded, because guarding only one leaves the other reachable and the user never moves.
- Re-running onboarding for testing requires temporarily forcing the guard in the root layout; there is no in-app reset.
