# Context

The Charter's Architectural Principles require the codebase to scale for years without major refactoring, isolate features, and keep business logic independent of the UI. React Native/Expo projects commonly default to organizing code by technical type (`components/`, `screens/`, `hooks/`) with business logic scattered through components and hooks. That pattern is fast to start with but becomes difficult to change safely as features accumulate, and makes it hard to test business rules (like streak calculation) without rendering UI.

---

# Decision

Adopt **Clean Architecture** (Domain, Data, Presentation, Platform layers with dependencies pointing inward) combined with **Feature-First organization** (each feature owns its own slice of each layer), as fully specified in `architecture/02-Architecture.md`.

---

# Alternatives Considered

- **Type-first organization** (`components/`, `screens/`, `services/` at the top level) — rejected: does not scale past a handful of features without becoming a tangle of cross-imports, and doesn't naturally separate business logic from UI.
- **MVVM without an explicit Domain layer** — rejected: tends to leak business logic into view-models/hooks over time without a hard architectural boundary preventing it.
- **No formal architecture, "just React Native conventions"** — rejected: directly conflicts with the Charter's explicit requirement for Clean Architecture and Feature-First organization.

---

# Consequences

**Positive:**

- Business logic (schedule interpretation, streak math) is unit-testable without any UI or database involved.
- A feature can be deleted or rebuilt by touching one folder plus its registration point, satisfying the Charter's "new features can be added with minimal refactoring" success criterion.
- The widget (`engineering/Widgets.md`) can reuse Domain-layer use cases directly, guaranteeing it never disagrees with the main app about business rules.

**Negative / Trade-offs:**

- More upfront structure than a type-first approach — a trivial feature still requires domain/data/presentation folders, which can feel like overhead for very small features.
- Requires discipline to enforce the Dependency Rule (`architecture/02-Architecture.md`'s Non-Negotiable Rules) — without review vigilance (`standards/Git-Workflow.md`), a component could still accidentally import the Data layer directly.
