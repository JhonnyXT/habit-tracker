# ADR-008 — Multi-Alert Reminders, Restricted to Daily Habits

# Context

ADR-005's decision #2 states "one reminder per habit." Reviewing a reference reminders app surfaced two features worth adopting on their own merits, independent of that app's broader (and out-of-scope) task-manager model: a pre-reminder that fires before the main time, and a follow-up that fires after it if the habit was not marked done. Both are opt-in, bounded nudges, not the open-ended alert chains the reference app offers.

The constraint that shaped the design: iOS caps an app at roughly 64 pending local notifications in total. A habit scheduled on specific weekdays already consumes up to 7 of those slots (`ExpoNotificationScheduler` schedules one `WEEKLY` trigger per selected day, per ADR-005). Adding a pre-reminder and a follow-up would triple that to 21 slots for a single weekday habit — a handful of such habits could silently exceed the ceiling, with no error surfaced anywhere; some reminders would simply never arrive.

---

# Decision

**1. Pre-reminders and follow-ups are offered only for daily-schedule habits.** `setHabitReminderUseCase` enforces this as a hard rule, not a UI convention: if `habit.schedule.type !== 'daily'`, any `preEnabled`/`followupEnabled` input is ignored and existing rows of those kinds are deleted. A daily habit only ever needs 1 notification slot per kind (a `DAILY` trigger, not one per weekday), so the worst case is 3 slots per habit — the same order of magnitude as today, not a multiplier on top of the weekday case that was already the largest consumer.

**2. Each kind is its own independent `Reminder` row with an absolute time, not an offset evaluated at schedule-time.** `Reminder` gained a `kind: 'main' | 'pre' | 'followup'` column. When a pre-reminder or follow-up is enabled, `set-habit-reminder.ts` computes its clock time once via `shiftClockTime(mainTime, offsetMinutes)` (fixed offsets: -15 min, +30 min) and stores that literal time. `ExpoNotificationScheduler`, `syncReminders`, and cancellation are all untouched — they already handle "a habit has N enabled reminders" generically, because `ReminderRepository.getForHabit` was always plural. This was simpler and lower-risk than teaching the scheduler port about offsets: the alternative considered was passing `kind`/`offsetMinutes` through `ScheduledReminder` and computing the effective hour/minute inside the adapter, which would have touched the one piece of platform-specific code in this feature area for no behavioural difference.

**3. Offsets are fixed, not user-configurable.** 15 minutes before, 30 minutes after. No picker, no stored offset value. This keeps the feature's UI surface to two switches and keeps the notification-count math simple to reason about (exactly 0-3 slots per daily habit, always).

**4. Editing a habit's schedule away from `daily` deletes its pre/follow-up rows.** `editHabitUseCase` was already rescheduling reminders after a name/schedule change; it now also drops any `pre`/`followup` rows when the new schedule is not `daily`, before rescheduling what remains. Without this, a habit switched from daily to weekdays would keep its old pre/follow-up rows, which would then multiply by the new weekday count on the very next `syncReminders` pass — reintroducing the exact problem decision #1 exists to prevent.

---

# Alternatives Considered

- **Offer multi-alert reminders on every schedule type, with no restriction** — rejected: the notification-count math above shows this can silently exceed the OS ceiling with a realistic number of habits, and a reminder that silently never arrives is worse than a feature that isn't offered.
- **Offer it everywhere, with a runtime counter that stops scheduling once a safe threshold is approached** — considered, rejected for v1: it trades a static, provably-safe limit (3 slots per habit, capped by construction) for a dynamic one that depends on how many other habits exist, is harder to reason about, and would need its own UI to explain why a toggle silently didn't take effect. Revisit only if daily-only turns out to be too restrictive for real usage.
- **User-configurable offsets** — rejected for v1 as unnecessary surface area; `Roadmap.md`'s "Less but Better" framing for this item favors two fixed, well-chosen defaults over a picker most users would never touch.
- **Passing `kind`/`offsetMinutes` through the `NotificationScheduler` port** — rejected in favor of computing the absolute time once in the use case layer (decision #2): same outcome, smaller diff, zero changes to the platform adapter.

---

# Consequences

**Positive:**

- The OS notification ceiling cannot be exceeded by this feature, by construction — there is no code path that schedules more than 3 slots for a single habit.
- `ExpoNotificationScheduler`, `syncReminders`, and the cancellation logic required no changes; the feature is entirely a domain/data addition plus a UI addition, which kept the change small and testable.
- Existing reminders (all `kind = 'main'` after the migration backfill) are unaffected.

**Negative / Trade-offs:**

- Weekday- and times-per-week-scheduled habits cannot get a pre-reminder or follow-up at all, even though they are arguably the habits that could benefit most (e.g. a gym habit on specific days). This is a deliberate scope cut, not an oversight — see `Roadmap.md`.
- Fixed, non-configurable offsets mean a user who wants "5 minutes before" instead of "15" has no way to get it in v1.
