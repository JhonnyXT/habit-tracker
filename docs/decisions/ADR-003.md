# ADR-003 — Use Zustand for Presentation-Layer State Management

# Context

`architecture/02-Architecture.md` requires a Presentation-layer state solution that holds only UI/derived state — never business logic — and stays lightweight, since this app has no server state/caching concerns typical of networked apps (no request de-duplication, no cache invalidation across a network boundary). The chosen tool needed to be simple enough not to become an abstraction the Charter would flag as unnecessary, while still giving Reanimated-driven, frequently-updating UI (e.g. toggling completions) fast, minimal-re-render updates.

---

# Decision

Use **Zustand** as the sole Presentation-layer state management library, per `engineering/State-Management.md`'s conventions: one store per feature, actions that delegate to Domain-layer use cases, no business rules inside stores.

---

# Alternatives Considered

- **Redux (with Redux Toolkit)** — rejected: designed around solving problems (complex middleware chains, time-travel debugging, large team coordination via strict boilerplate) this app's scale doesn't have; would add ceremony without commensurate benefit, conflicting with the Charter's "avoid unnecessary abstractions."
- **React Context + useReducer only** — rejected: works for small cases but tends to cause broad re-renders without careful memoization, and lacks Zustand's ergonomic selector-based subscription model needed for smooth 60 FPS interactions (NFR-1.1) on frequently-toggled state like today's habit list.
- **A server-state library (e.g. React Query/TanStack Query)** — rejected: solves server-state caching/synchronization problems that do not exist in this app, since there is no server (ADR-002) — would be solving for a problem class the product doesn't have.
- **Recoil / Jotai (atom-based state)** — considered comparable in simplicity to Zustand; Zustand was chosen for its simpler mental model (plain stores + actions vs. atom graphs) matching the relatively small number of independent state slices this app needs (one per feature, per `engineering/State-Management.md`).

---

# Consequences

**Positive:**

- Minimal boilerplate; store shape stays close to plain TypeScript, easy for any contributor (or AI assistant) to read without framework-specific ceremony.
- Selector-based subscriptions keep re-renders scoped, supporting the 60 FPS requirement (NFR-1.1) for interactions like toggling a habit.
- Naturally fits the "one store per feature" convention already established in `engineering/State-Management.md`, reinforcing Feature-First organization (ADR-001).

**Negative / Trade-offs:**

- Less prescriptive structure than Redux means store discipline (no business logic inside actions) relies on `standards/Coding-Standards.md` review vigilance rather than being enforced by the library itself.
- Smaller ecosystem of middleware/dev tools compared to Redux, though none of those extras are currently needed given this app's scope.
