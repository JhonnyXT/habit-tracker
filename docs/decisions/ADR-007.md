# ADR-007 — Build Variants Come From Dynamic Config, Not Gradle Product Flavors

# Context

`operations/Deployment.md` and `operations/Environment.md` both describe three build profiles, but the repository had exactly one build identity: a static `app.json`, a single `com.habittracker.app`, and a build produced by hand with `expo prebuild` followed by `./gradlew assembleDebug`. Three consequences followed from that.

The development build and any stable build could not coexist on the phone, because Android keys installations by `applicationId`. Every QA pass therefore ran against the developer's real habit history — the one thing `00-Project-Charter.md` treats as the user's own data. And the documented profiles were aspirational, which `CLAUDE.md`'s fifth rule forbids.

The obvious way to give an Android app several identities is Gradle `productFlavors`. That option is unavailable here: `/android` is in `.gitignore`, so the project runs on Continuous Native Generation and the native project is regenerated from config on every `prebuild`. Hand-written flavors in `android/app/build.gradle` would survive exactly until the next prebuild.

---

# Decision

**1. Three variants — `dev`, `test`, `prod` — each with one reason to exist.**

| Variant | Reason to exist | Built by | Signed with |
|---------|-----------------|----------|-------------|
| `dev` | Iterating. Dev client, Metro, Fast Refresh. | `scripts/build-android.sh dev` → `assembleDebug` | debug keystore |
| `test` | Verifying before publishing. Standalone APK, JS bundle embedded, no Metro, real release build. | `scripts/build-android.sh test` → `assembleRelease` | debug keystore |
| `prod` | Publishing. Signed AAB. | `eas build --profile prod` | EAS-managed upload key |

**2. Identity comes from `app.config.ts` reading `APP_VARIANT`.** `app.json` was replaced by a typed `app.config.ts` holding a table of three entries — name, `applicationId`, URL scheme, adaptive-icon background. An unrecognised `APP_VARIANT` throws rather than silently falling back, so a typo in a build command fails at config resolution instead of producing a mislabelled APK.

**3. `dev` keeps `com.habittracker.app`; `prod` takes `com.habittracker`.** The install already on the maintainer's device holds real habit history, and it is a development build. Keeping its `applicationId` and its `habittracker` scheme means adopting variants costs no data and breaks no notification deep link. `test` and `prod` are new IDs and start empty.

**4. `test` is signed with the debug keystore.** It is installed by `adb`, never by Play, so a real upload key would buy nothing and would mean a secret in the repository or in the build script. Production signing is EAS's responsibility, which is also why `scripts/build-android.sh` refuses `prod` outright instead of producing an unpublishable "prod" APK.

**5. Per-variant databases fall out for free.** A distinct `applicationId` means a distinct app sandbox, so all three variants can keep the same `habit-tracker.db` filename with no risk of sharing rows.

**6. The variant is readable at runtime through `src/core/config/`.** `app.config.ts` writes it into `extra.appVariant`; `appVariant`, `isDev`, `isTest`, `isProd` read it back via `expo-constants`. Settings shows a "Tipo de build" row on `dev` and `test` and hides it on `prod`, so a QA session can never be in doubt about which build is on screen.

# Alternatives Considered

- **Gradle `productFlavors`** — the standard React Native answer, and the one Expo documents for projects *not* using Continuous Native Generation. Rejected because `/android` is generated and gitignored; the flavors would be erased by the next `prebuild`. Adopting them would mean committing `android/` and giving up CNG, a far larger change than the problem justifies.
- **`prod` keeping `com.habittracker.app`, `dev` moving to `com.habittracker.app.dev`** — the more conventional layout, and the one to prefer in a new project. Rejected here because it would strand the existing install's history under a package no variant claims. Swapping later is possible but costs an `adb run-as` database migration.
- **Varying the SQLite filename per variant** — unnecessary given decision 5, and it would put a build concern inside `core/data`.
- **A fourth "staging" variant** — rejected. `00-Project-Charter.md`'s *Less, but Better* applies to tooling too, and with no backend (`ADR-002.md`) there is no staging environment for it to point at.

# Consequences

**Positive:**

- All three builds coexist on one device, distinguishable in the launcher by name and adaptive-icon background without any new image assets.
- QA runs against an empty `test` install, so the maintainer's real history is no longer test data.
- `operations/Deployment.md` and `operations/Environment.md` now describe commands that exist.
- Adding a per-variant difference later is a line in one table, not a change in two build systems.

**Negative / Trade-offs:**

- **Switching variants locally requires `prebuild --clean`**, because the `applicationId` is written into the generated native project. `scripts/build-android.sh` always does this, which makes every local build a full native build — minutes, not seconds. JS-only work stays on `dev` with Fast Refresh and pays this cost only when crossing variants.
- `test` APKs are debug-signed, so they cannot be uploaded to Play and will not install over a Play-signed build.
- `prod` is only reachable through EAS, so publishing requires `eas login` and a network connection — deliberate, since it is also what keeps the upload key out of the repository.
- The `prod` `applicationId` is permanent once published. Revisiting decision 3 is cheap today and impossible after the first Play release.
