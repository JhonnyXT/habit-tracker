# Purpose

Verify, systematically, that the application satisfies every User Story's acceptance criteria (`requirements/User-Stories.md`), every Functional Requirement (`requirements/Functional-Requirements.md`), and every Non-Functional Requirement (`requirements/Non-Functional-Requirements.md`) — after Optimization (`06-Optimization.md`) and before Principal Engineer Review (`08-Principal-Engineer-Review.md`).

---

# QA Philosophy

- QA verifies against written acceptance criteria, not vibes — every test case traces back to a US-xx, FR-x, or NFR-x reference.
- A feature is not "probably fine" — it is verified explicitly or it is not done, per `standards/Definition-of-Done.md`.
- Regressions are treated as seriously as new bugs — re-run the full suite below after any change, not only targeted tests.

---

# Test Categories

## 1. Functional Verification (per User Story)

Walk every story in `requirements/User-Stories.md` (US-01 through US-23) and confirm its acceptance criteria holds on-device, on both iOS and Android. Document pass/fail per story, per platform.

## 2. Functional Requirement Verification

Confirm each FR in `requirements/Functional-Requirements.md` directly, including edge cases the story format might not spell out:

- FR-2.3 / FR-5.3 — attempt to mark a future date; must be rejected/non-interactive.
- FR-4.1–FR-4.4 — construct known completion patterns and verify streak math by hand against the app's displayed value.
- FR-9.2 — attempt to import a deliberately corrupted export file; must fail safely with no partial state.

## 3. Non-Functional Verification

- NFR-1 (Performance) — confirm the results recorded during `06-Optimization.md` still hold after any subsequent change.
- NFR-2 (Offline-First) — put the device in airplane mode and exercise every V1 feature; nothing should degrade.
- NFR-3 (Reliability) — force-quit mid-write scenarios (where feasible to simulate) and confirm no data loss or corruption.
- NFR-4 (Privacy) — confirm via network inspection that no requests are made beyond OS-level services.
- NFR-5 (Accessibility) — see dedicated section below.

## 4. Accessibility QA (Dedicated Pass)

- Navigate the entire app using only VoiceOver (iOS) and only TalkBack (Android) — every screen, every action, no exceptions (FR-10.1, US-21).
- Set the system font size to its largest accessibility setting and confirm no truncation/overlap on any screen (FR-10.2, US-22).
- Enable Reduced Motion at the OS level and confirm all animations degrade per `design/Motion.md` (FR-10.3, US-23).
- Confirm every touch target meets platform minimums using accessibility inspection tools (FR-10.4).
- Confirm no screen relies on color alone to communicate state (NFR-5.4).

## 5. Cross-Surface Consistency

- Confirm the Today screen, Habit Detail, and the home screen widget always agree on a habit's state, per `design/UX-Principles.md`'s Consistency Across Surfaces principle.

## 6. Platform & Device Matrix

- Test on the current and immediately prior major OS version of both iOS and Android (NFR-7.1).
- Test on at least one phone-class and one tablet-class device/simulator per platform (NFR-7.2).
- Confirm graceful widget degradation on any OS version lacking required widget APIs (NFR-7.3).

## 7. Appearance

- Verify every screen in both light and dark mode (US-18), including the manual override persisting across restarts.

---

# Regression Policy

Any change made to fix a bug found during QA requires re-running:

- The full story list for the affected feature.
- The full Accessibility QA pass if the change touched UI structure or motion.
- The relevant Optimization benchmarks if the change touched a Domain use case or Data-layer query.

---

# Exit Criteria

QA is complete when every story, functional requirement, and non-functional requirement above is verified with a recorded pass on all supported platforms/devices, and every discovered defect is either fixed and re-verified or explicitly triaged and accepted by the team before proceeding to `08-Principal-Engineer-Review.md`.
