# Purpose

Define the technical mechanics of turning reviewed, approved source code into a submitted app store build — the "how," complementing `operations/Release-Process.md`'s "when/in what order."

---

# Build Tooling

- **Continuous Native Generation.** `/android` and `/ios` are gitignored and regenerated by `expo prebuild` from `app.config.ts`. Native project files are never edited by hand; a change that needs to reach the native project goes into config or a config plugin (`decisions/ADR-007.md`).
- **`scripts/build-android.sh`** produces the local `dev` and `test` Android builds end to end: prebuild, Gradle, `adb install`.
- **EAS Build** produces the production binary, holding the upload key so it never enters the repository.
- **EAS Submit** handles submission to Google Play, avoiding manual Android Studio submission steps for routine releases.

---

# Build Variants

Three variants, defined by the table at the top of `app.config.ts` and selected with the `APP_VARIANT` environment variable. Each has a distinct `applicationId`, so all three install side by side on one device (`decisions/ADR-007.md`).

| Variant | Application ID | Command | Output |
|---------|----------------|---------|--------|
| `dev` | `com.habittracker.app` | `npm run build:dev` | Debug APK, dev client + Metro |
| `test` | `com.habittracker.app.test` | `npm run build:test` | Release APK, JS bundle embedded, no Metro |
| `prod` | `com.habittracker` | `npm run eas:prod` | Signed AAB for Play |

- **`dev`** — local iteration. Fast Refresh, debug tooling, verbose logging (`standards/Logging.md`).
- **`test`** — pre-release verification (`reviews/07-QA.md`) on real devices without going through store review. A real release build (minified, no Metro), debug-signed because it is installed by `adb`, not by Play. This is the profile earlier revisions of this document called "Preview".
- **`prod`** — the exact build submitted to Google Play, produced only after `reviews/08-Principal-Engineer-Review.md` and `reviews/Release-Checklist.md` are complete.

Switching variants locally forces a full native rebuild, because the `applicationId` is written into the generated native project. `scripts/build-android.sh` always runs `prebuild --clean` for this reason.

# Build Process

1. Confirm the release branch/tag is the exact commit that passed `reviews/08-Principal-Engineer-Review.md` — never build from an uncommitted or divergent working copy (`reviews/Release-Checklist.md`).
2. Apply the version bump per `operations/Versioning.md` before building.
3. Produce a `test` build first for final device verification (`reviews/Release-Checklist.md`'s Final Device Verification section) — fresh install and upgrade-path testing both happen here.
4. Once verified, produce the `prod` build from the same source commit — not a separately modified build — so what was verified is exactly what ships.
5. Submit via EAS Submit to Google Play.

Note that step 3 and step 4 produce different `applicationId`s, so a `test` APK cannot be promoted to production; the `prod` build is always built fresh from the verified commit.

# Widget & Notification Entitlements

- Native capabilities (notification entitlements, widget app group / shared storage configuration per `engineering/Widgets.md`) are configured through Expo config plugins checked into the repository — not manually toggled in Xcode/Android Studio per build, which would risk configuration drift between builds.

---

# Store-Specific Considerations

- **iOS:** not built today. `app.config.ts` carries the iOS config, but only Android variants are wired up; adding iOS means giving each variant a `bundleIdentifier` in the same table.
- **Android:** Google Play's staged rollout capability is used where available, allowing a release to reach a subset of users first — relevant to `operations/Release-Process.md`'s Rollback section (halting a staged rollout is the closest available mechanism to a rollback).

---

# What Is Explicitly Not Part of Deployment

- There is no backend/server deployment step — per `decisions/ADR-002.md`, this application has no server component to deploy.
- There is no remote configuration/feature-flag deployment — no such system exists in V1 (`decisions/ADR-004.md`'s no-remote-telemetry stance extends to not introducing a remote config service either, absent a dedicated future ADR).
