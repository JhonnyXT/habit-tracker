# Habit Tracker

Local-first habit tracking app. React Native + Expo + TypeScript. Android dev build running on a physical device.

## Active initiative: Expo SDK 54 → 57 upgrade, then adopt Expo UI

Developed directly on `main` (the `expo-sdk-57-upgrade` branch that started this work is abandoned — left in place on GitHub but not synced further; don't build on it). Goal: real platform-native controls — SwiftUI on iOS, Material 3 on Android, from one component tree — via `@expo/ui`, per `docs/research/expo-ui.md`'s recommendation. This reads directly on the Charter's own **Native First** / **Platform Fidelity** principles (`00-Project-Charter.md`, `03-Design-System.md`): this app is *supposed* to look native per platform, not identical across both. `@expo/ui` has no release for SDK 54 (jumps 55→56/57), so the SDK bump is a prerequisite, done before touching any screen.

Note the overlap with the NativeWind initiative below: NativeWind is a *styling* system (Tailwind classes on regular RN views, still JS-rendered); `@expo/ui` renders *actual* native views. They're two different answers to the same "Native First" goal. Reconciling which one Settings ends up on (it currently runs NativeWind) is part of this initiative's job once the pilot lands — not decided yet.

**Step 1 (SDK bump) is done.** Now on SDK 57 (`react` 19.2, `react-native` 0.86.2, `expo-router` ~57.0.12, `react-native-reanimated` 4.5.1, `react-native-worklets` 0.10.1, `react-native-gesture-handler` ~2.32, `expo-notifications` ~57.0.10, TypeScript ~6.0.3). Requires **Node 22.13+** to build (`.nvmrc` pins `22`; this machine's system Node was 20.x, installed 22 via nvm — run `nvm use` before any `npm`/`npx expo` command in a new shell). What the bump actually touched:

**Step 2 (device verification) is in progress.** Installing the APK and a first launch found a real crash, now fixed: `DraggableHabitList`'s `containerStyle` worklet read `items.length` directly, which makes the worklet's UI-thread closure capture the *whole* `items` array — an array of `TodayHabit`, each carrying a `Habit` with `Date` fields (`createdAt`/`updatedAt`). `react-native-worklets` 0.10 (SDK 57) rejects `Date` during closure serialization where older versions were laxer, so this crashed every load of Today with `[Worklets] Cannot copy value of type 'Date'.` Fixed by reading `items.length` into a plain number before the worklet. Still not verified: reminders (schedule + fire + deep link, both main and multi-alert), Today's other gestures (drag-to-reorder, swipe, tap-to-expand — the habit-row `GestureTap` nesting from point 11, `TaskCard`'s swipe), the Sistema/Claro/Oscuro appearance toggle, and Settings' NativeWind screens. ## Active initiative: Reminderos-inspired redesign (merged into `main` from branch `reminderos-redesign`; still active, now developed directly on `main`)

The NativeWind design-system work below (previously branch `nativewind-obytes`) is **merged into `main`** — Settings runs on it; every other screen is still `core/theme`. That initiative is paused, not abandoned; the section is kept for context on `core/ui-nw/`.

The current branch adopts specific interaction and visual patterns from a reviewed reference app ("Reminderos," an iOS reminders app) **without adopting its product scope** — this app stays a habit tracker with streaks, not a task manager. Per-feature detail lives in ADRs/Roadmap; the load-bearing decisions and bugs found:

1. **`habit-form.tsx` is now a native form sheet**, not a full-screen push. `src/app/_layout.tsx`'s `Stack.Screen` for it uses `presentation: 'formSheet'` + `sheetAllowedDetents`/`sheetGrabberVisible`/`sheetCornerRadius` — all native to `react-native-screens` ~4.16 / `expo-router` ~6, no library added. iOS gets the real drag-handle/detent behaviour; Android's support is more limited and unverified on hardware (no iPhone/Mac access, same standing limitation as the rest of this app's iOS work). **Scope narrowed in point 16:** this route is now edit-only (`?id=`) — creating a habit or task no longer goes through it at all, see point 16's `create-sheet.tsx`.
2. **The form's Icon/Color/Horario/Recordatorio sections became chips** (`core/ui/chip.tsx`) that expand inline on tap instead of always-visible blocks — an accordion (`activeReveal` state), not real nested sheets, to avoid the risk of stacking `formSheet`s untested on this device.
3. **The "+" on Today/Habits is now a dual entry point.** A `SegmentedControl` at the top of the sheet (Hábito/Tarea, "Hábito" preselected) switches the form's content; choosing "Tarea" swaps in a name field + a habit picker (disabled with a note if no habits exist yet — a task can never be created without a parent habit).
4. **Habit Tasks** (`FR-11`, `Roadmap.md`): a habit may have repeatable daily tasks. New tables `tasks`/`task_completions` (migration v3), new domain files under `features/habits/domain/` (`entities/task.ts`, `task-progress.ts`, `use-cases/*-task*.ts`), a `getHabitTasks` use case, and a small progress bar on Today/Habits rows. **Reversed later in this same initiative:** tasks were originally deliberately never-gating the streak (structural — no shared code path with `computeStreaks`); the product decision changed to the opposite — completing 100% of a habit's tasks for the day now auto-completes the habit itself, so the streak *does* pick it up. See point 10 below for the current behavior; this point is kept for the migration/table history.
5. **Multi-alert reminders, restricted to daily habits only** (`ADR-008.md`, `FR-6.5`): `Reminder` gained a `kind: 'main' | 'pre' | 'followup'` column. A pre-reminder (-15 min, fixed) and a follow-up (+30 min, fixed) can be enabled **only** when `habit.schedule.type === 'daily'`, enforced in `set-habit-reminder.ts` itself, not just in the UI — a weekday-scheduled habit already reserves up to 7 OS notification slots (one `WEEKLY` trigger per day per `ADR-005.md`), and iOS caps an app at ~64 pending local notifications total; letting multi-alert multiply that would risk silently exceeding the ceiling. `editHabitUseCase` was fixed to drop any `pre`/`followup` rows if a habit's schedule changes away from `daily`, closing the one path that could have reintroduced the multiplier. `getHabitReminder`/`archiveHabitUseCase`/`editHabitUseCase` also had a latent `reminders[0]` bug (silently ignored every reminder past the first) fixed as part of this — pre-existing, not introduced here.
6. **Today's empty state got a full visual pass**: a "+" FAB (plain light circle, soft neutral shadow, no colored border/halo) fixed bottom-right, aligned with the tab bar; a search field (filters the visible list by name, disabled/dimmed when the list is empty) and a "..." menu (Ver archivados, Exportar copia) replacing the old inline add button; and a mocked "card deck" illustration (`empty-today-preview.tsx`) shown **only** when the user has zero habits ever — a separate, plainer message covers "habits exist, none due today" so the illustration never lies about there being nothing to see.
7. **Real Reanimated bug found while building the card-deck illustration**: `Animated.View style={[{transform: [...]}, animatedStyle]}` does not merge the two `transform` arrays — React Native replaces the whole `transform` property with whichever style object in the array defines it last, so the animated style silently discarded the static `rotate`/`translateX`. Fix: bake every transform (static and animated) into the *same* `useAnimatedStyle` return value. Same root cause independently documented in `my-wallet-app`'s `useFloat` hook.
8. **`TabBar` reserves width for the FAB on screens that have one** (`screensWithFab` set, checked against `state.routeNames[state.index]`), instead of centering itself across the full screen width regardless — otherwise the tab pill centers alone and the [pill + FAB] group reads as off-center once the FAB's footprint is added next to it.
9. **The reminder time picker (`habit-form.tsx`) is a fully custom component (`core/ui/wheel-time-picker.tsx`)**, not `@react-native-community/datetimepicker`. Two real problems drove this, not a cosmetic preference: (a) on Android, that library's `display="spinner"` still opens as a native `TimePickerDialog` — never inline — and only fires `onChange` once, on OK/Cancel; the original code assumed continuous `onChange` like iOS's inline spinner and never closed the dialog, so tapping OK visibly did nothing (fixed properly by checking `event.type === 'set'` before applying the value and always closing on Android); (b) Android's native dialog chrome can't be restyled at all, so matching a designed look required owning the rendering. `WheelColumn` learned a real perf lesson in the process: initial version rendered all 60 minute values in a plain `ScrollView` (60 mounted `PressableScale`s, each its own Reanimated worklet) and used `contentOffset` as a *reactive* prop, which fights the scroll gesture on every re-render mid-swipe. Fixed by switching to a virtualized `FlatList` (`getItemLayout` + `initialScrollIndex`, only ~5 items ever mounted) with plain (non-animated) `Pressable` items, and `React.memo` on the column so changing the hour doesn't re-render the minute column. The picker opens as a real modal dialog (scrim + `ZoomIn`, same pattern as `ConfirmDialog`) when tapping the "Hora" row, not inline. Time displays 12h with AM/PM (`Intl.DateTimeFormat('es', { hour12: true })`) everywhere in the UI; the stored `ClockTime` stays 24h `"HH:mm"` internally since that's what scheduling needs — only the display layer changed.
10. **Habit Tasks gained `color`/`urgent`/`pinned`/`deadline`** (migrations v5/v6), set from a "Fecha límite" + "Personalizar" chip pair in the "+" entry point's Tarea mode — mirrors the reference app's Deadline/Customise chips, adapted to this app's fixed 8-color palette instead of a free 33-swatch picker. `DeadlineCalendar` (`features/habits/presentation/components/deadline-calendar.tsx`) is a deliberate sibling to `MonthCalendar`, not a shared component with a mode flag: `MonthCalendar` marks days after today as `future` (disabled, since you can't back-fill completions) and forbids navigating past the current month, while a deadline is the opposite — days *before* today are disabled and future months must stay reachable. Threading that through one component as a boolean would've been more confusing than two small pure functions (`buildMonthGrid` vs `buildDeadlineMonthGrid` in `domain/calendar.ts`).
11. **Habit Tasks moved onto Today itself, nested inside each habit's own row, not a standalone list.** Went through two designs before landing here: first a flat cross-habit "Tareas" section (its own `getTodayTasksUseCase`, a `TaskListFilterSheet` "Listas" filter) — both deleted once the direction changed to per-habit expansion, since a flat list duplicated the habit row right above it. Tapping a habit row (the name/subtitle area, not the checkbox) expands it in place to reveal its tasks as `TaskCard`s (pastel card, checkbox, deadline row — see point 12 for how editing/deleting a task actually works, that changed after this). `getTodayHabitsUseCase` now embeds each habit's own `tasks: TaskWithState[]` directly on `TodayHabit` instead of a separate query.
    - **Checkbox vs. row-tap had to be split.** Before this, tapping *anywhere* on a habit row toggled it complete (intentional, for accessibility — "double tap to mark done"). That can't also mean "expand" for habits with tasks, so `HabitRow` now wraps `CompletionCheck` in its own tap target with the completion toggle, and the row's own tap (in `DraggableHabitList`) means "toggle expand" for habits that have tasks, or nothing at all for habits that don't. **A real crash came out of this**: the checkbox (and later the task card's own controls) are nested *inside* the row's `GestureDetector`. A plain RN `Pressable` nested there does **not** reliably win the touch over the parent's RNGH `Tap`/`Pan` gesture — both recognizers can fire for the same touch, since RN's responder system and RNGH's native recognizers are separate systems that don't coordinate automatically. The fix is `core/ui/gesture-tap.tsx` (`GestureTap`): a nested `GestureDetector` with its own `Gesture.Tap()`, which *does* correctly win against an ancestor detector by RNGH's default nested-detector precedence. Used for the habit checkbox. (Task cards ended up not needing it — see point 12, their swipe gesture requires >15px movement to activate, so a plain tap never engages it and plain `Pressable`s are safe there. **This reasoning was incomplete and caused a real bug later — see point 19.**) The outer row's accessibility role/hint is suppressed (`accessible={false}`) for non-expandable habits, since claiming `role="checkbox"` there would be a lie — nothing happens when you tap the row body anymore, only the nested checkbox does something.
    - **`DraggableHabitList` supports one row expanding to a taller height without breaking drag-to-reorder**, which positions rows with fixed-height absolute math (`top = livePosition × slot`) for its spring physics. Rather than rewrite that into a general dynamic-height/prefix-sum system, the fix stays narrow because only one row can ever be expanded at a time (`expandedId`, mirroring the existing single-row-open `openId` pattern for swipe): a single `extraHeightSV` shared value tracks the current animated expansion height, and any row whose live position is after the expanded one just adds `extraHeightSV.value` to its own `top`; the container height and the separator lines read the same value so everything shifts in sync. **Starting a drag on any row collapses whatever is expanded first** (`onDragStart` → `collapse()`), a deliberate scope-narrowing so drag physics never has to account for a mid-animation height change — chosen over teaching the position math to handle both at once, which was the higher-risk option.
    - **Completing every task for a habit on a given day now auto-completes the habit itself** — direct reversal of point 4's original "never gates the streak" rule, by explicit later product decision. `toggleTaskCompletionUseCase` (now takes `tasks`/`habits`/`completions` too, not just `taskCompletions`) recomputes the habit's same-day task completion count after every toggle and upserts a `Completion` row when it hits 100%. This only ever pushes a habit *toward* completed — unchecking a task afterward deliberately does **not** un-complete the habit, since the habit's own completion can still be toggled independently of its tasks and silently reversing it would be surprising. Task edit reuses `habit-form.tsx` in a new `?taskId=` mode (`getTaskUseCase`, `editTaskUseCase`) rather than a separate screen — the habit picker section hides itself when editing a task, since reassigning a task to a different habit isn't supported.
12. **Today's habit-list visual and interaction model went through several corrections after the initial expand-in-place build (point 11), all in direct response to on-device testing:**
    - **Every habit row is tinted with its own habit color at all times** (`theme.colors.habit[habit.color].tint`), not just white/neutral-when-collapsed as one intermediate version had it — reverted back to "always tinted" per explicit direction. `HabitRow` also only has **one** layout now (icon well on the left, checkbox + expand chevron on the right) used both collapsed and expanded; an earlier version swapped the checkbox to the top-left only when expanded to mirror a reference image, which regressed the round icon well being visible at all — not worth the complexity for a cosmetic detail, reverted to the single layout.
    - **Habit rows on Today read as individually separated cards, not one continuous card with hairline dividers.** `DraggableHabitList` is called with `separators={false}` and `slot={HABIT_ROW_HEIGHT + CARD_GAP}`; each `renderItem` wraps its row in a `paddingBottom: CARD_GAP` view (same pattern `habits.tsx` already used for `HabitCard`). This only works if the row's own swipe layer doesn't paint an opaque background over that gap — see next point.
    - **Habit-level swipe-to-edit/delete was removed from Today entirely** (`onEdit`/`onDelete` no longer passed to Today's `DraggableHabitList` call) — by explicit decision, editing/deleting a habit now only happens from the Hábitos tab (already fully supported there via Habit Detail → edit → the form's own delete button; nothing new had to be built). This was also the fix for a real visual bug: `DraggableRow`'s swipe layer used to paint an opaque `surface.secondary` background across its *entire* slot height (including the new gap-for-separation area) whenever the row was swipeable, so enabling per-card gaps while swipe was still active left a stray opaque/mismatched patch in the gap next to the reveal buttons. Removing habit-level swipe sidesteps the conflict instead of solving the general case.
    - **Task edit/delete moved from a "•••" action-sheet Modal to swipe-to-reveal directly on `TaskCard`** (left reveals delete, right reveals edit — same visual language as the old habit-row swipe). The Modal approach is gone; `TaskCard` now owns its own `Gesture.Pan()` swipe, structured as `Animated.View(exiting/layout for the delete animation) > View(overflow:hidden, the actual clip boundary) > [reveal-buttons layer, GestureDetector-wrapped card content]` — layout-animation concerns and swipe-clipping concerns were deliberately split onto two different nodes after combining them on one node produced a visual glitch (the edit icon rendering outside the card's bounds); still worth confirming fully fixed on-device. **Reversed later in this same initiative:** these icons originally shipped bare — icon only, no colored circle behind them — per explicit feedback at the time that the circle badge looked wrong. After further on-device testing the bare icons read as visually broken instead (no rounded, tinted well behind them, unlike every other icon in the app), so `TaskCard`'s edit/delete reveal icons now sit in a 36px `radius.full` tinted circle (`accent.subtle` for edit, `state.dangerSubtle` for delete), matching the habit-row swipe pattern this initiative had deliberately diverged from. Don't re-remove the circle without asking first — this is now the second reversal on this exact detail.
    - **`sheetAllowedDetents: 'fitToContents'` was tried and reverted back to `[0.9]`.** The goal was letting the task-edit sheet size itself to its (much shorter) content instead of always being 90% of the screen tall. Suspected cause of failure: `habit-form.tsx`'s content sits in a `ScrollView`, which typically reports its *container* size rather than its *content's* intrinsic size for native layout-measurement purposes — `fitToContents` likely computed a near-zero height, so the sheet opened but was imperceptible ("no pasa nada" when tapping Editar). Reverted to the known-working fixed detent; the excess whitespace on short content (e.g. editing a task) is back but the sheet reliably opens. A real fix (either a non-ScrollView layout for short forms, or a fully custom Modal-based edit sheet instead of a native formSheet route) is still open — see "Next up" below.
13. **Two more corrections after further on-device testing of the task-delete flow and the task-edit sheet, both in direct response to user feedback:**
    - **Deleting the last task under an expanded habit used to make the row snap closed before the delete animation could be seen.** First-pass diagnosis was `DraggableHabitList`'s `canExpand` gating both the tap-to-toggle behaviour *and* (indirectly, via `HabitRow`'s `expandable` prop passed from Today) the chevron/expand affordance on `entry.tasks.length > 0`. Fixed two ways at the time: (a) `useHabitsStore.deleteTask` became a dedicated store action that patches the affected habit's `tasks` array in place instead of the delete flow calling a full `loadToday()`; (b) `DraggableHabitList` computes `itemCanExpand` as `(canExpand?.(item) ?? false) || expandedId === id`, and Today passes `expandable={entry.tasks.length > 0 || expanded}` to `HabitRow`. **This turned out to be necessary but not sufficient — the row still visibly closed before the animation played, per further on-device testing.** The actual root cause (found later, see point 14) was unrelated to `canExpand`: it was the expanded-content container's `overflow: 'hidden'` clip shrinking in sync with the *now-shorter* measured content, faster than the removed `TaskCard`'s own `FadeOut` could finish.
    - **The task-edit sheet was redesigned to match a reference ("Edit Reminder" bottom sheet) the user shared: a card with an inline circular checkbox-style marker + editable title, and a notes/description textarea below it**, replacing the plain labeled name `TextInput` — but **only in `?taskId=` edit mode**; task *creation* still uses the original labeled-field layout, since the reference was specifically about editing an existing task. This closes the "task-edit experience needs a design decision" item from a previous version of this doc. Scope was deliberately narrowed on the reference's "Subtasks" and "Attachments" sections — dropped entirely rather than built as inert placeholders, since neither concept exists in the domain and building either for real (subtask lists, file attachments) is a separate feature, not a layout change. `Task` gained a `notes: string | null` field (migration v7, `ALTER TABLE tasks ADD COLUMN notes TEXT`) threaded through `create-task`/`edit-task`, the mapper, the SQLite repository, and `core/domain/backup.ts` (`withTaskDefaults`/`isBackupTask`, so older backups without `notes` still restore). **The deadline/customize chip row below the new card was itself reworked one iteration later — see point 14.**
14. **Three more fixes after a second round of on-device testing, all direct user feedback on point 13's work:**
    - **The real root cause of the delete-animation clip (see point 13) was `DraggableRow`'s `onExpandedLayout`.** It re-measures the expanded content's height on every layout pass and springs `extraHeightSV` — which drives both the row's own `height` *and* its `overflow: 'hidden'` clip boundary — straight to the new value. The instant a task is removed from `entry.tasks`, React reconciles the list (correctly keeping the deleted `TaskCard` mounted as a Reanimated `exiting` ghost for its `FadeOut`), but the *measured layout height* of the wrapping view already reflects the smaller post-removal content in that same frame, since Reanimated's exit ghost doesn't reserve layout space — only paints on top. The container's clip was shrinking around the still-fading ghost, cutting it off. Fixed with a one-line asymmetry in `onExpandedLayout`: `extraHeightSV` still springs to a *larger* value immediately (content growing has nothing to clip), but a spring to a *smaller* value is wrapped in `withDelay(duration.listItemExit, …)` — giving the exiting `TaskCard` time to finish its fade before the clip catches up. `duration.listItemExit` (200ms, `core/theme/motion.ts`) is the same constant `TaskCard`'s own `FadeOut` uses, so the two are guaranteed to stay in sync rather than being two independent magic numbers that could drift apart.
    - **Tapping a `TaskCard`'s body (not its checkbox, not a swipe-revealed action) now opens `TaskDetailSheet`** (`features/habits/presentation/components/task-detail-sheet.tsx`) — a small centered `Modal` (same `FadeIn`/`ZoomIn` scrim pattern as `ConfirmDialog`) showing the task's name, deadline, urgent/pinned flags, and notes (or a placeholder if empty), plus an "Editar" button. This is a pure read path — no new domain use case, `TaskWithState` already carries everything the sheet displays. The body wraps a plain `Pressable` (not `GestureTap`) around the name/deadline column, same reasoning as the rest of point 12: `TaskCard`'s swipe `Gesture.Pan()` only activates past 15px of horizontal movement, so a tap never engages it and a plain `Pressable` is safe there. **Its "Editar" target changed in point 15** — no longer the `?taskId=` route.
    - **The task-edit sheet's "Personalizar" section (color/urgent/pinned) moved out of its inline accordion reveal into its own full-screen `Modal`**, per explicit direction: the sheet was "too long," and the reference interaction was a main-sheet-closes/sub-sheet-opens handoff, not an inline expansion. Tapping the "Personalizar" chip opened a second, separate `Modal` layered on top of the task-edit sheet. **Superseded one iteration later — see point 15:** further testing showed the sheet was *still* too tall (a native `formSheet` fixed at 90% height, regardless of how short the content got), and the next round of feedback removed "Personalizar" and its color picker from task editing entirely rather than continuing to shrink it. This sub-modal pattern survives only for **task creation**, which still runs through `habit-form.tsx`'s original chip-accordion flow, untouched by point 15.
15. **A third round of on-device feedback retired task editing from `habit-form.tsx` entirely and replaced the delete-animation fix with a deterministic version:**
    - **`TaskEditSheet` (`features/habits/presentation/components/task-edit-sheet.tsx`) is a dedicated, custom `Modal` — not a native `formSheet` route.** This is the fallback point 12/14 both flagged as the real fix if the `[0.9]` fixed-detent whitespace ever became a real complaint, and it did: the redesigned card content (points 13-14) was consistently shorter than 90% of the screen on-device, leaving a large dead zone above the "Guardar tarea" button no matter how much was trimmed from the content. `TaskEditSheet` is a bottom-anchored card (`justifyContent: 'flex-end'`, `maxHeight: '85%'` with an inner `ScrollView`) — ordinary RN layout, sized to its actual content, with zero dependency on native sheet-detent measurement. The `?taskId=` query param and every piece of `habit-form.tsx` state/logic that only existed to support it (`isEditingTask`, the task-loading `useEffect`, the edit branch of `onSave`) were deleted rather than left dormant — `habit-form.tsx` now only ever creates a task or creates/edits a habit; editing an existing task is `TaskEditSheet`'s job alone, opened directly from `(tabs)/index.tsx` (`editingTask` state) by both `TaskCard`'s swipe-edit icon and `TaskDetailSheet`'s "Editar" button — no more `router.push`/`router.back` round-trip for this flow. A new `useHabitsStore.editTask` action wraps `editTaskUseCase` and refreshes `today` on success, mirroring the `deleteTask`/`toggleTask` actions already there.
    - **`TaskEditSheet`'s content is deliberately narrower than what `habit-form.tsx` used to offer in edit mode**, per explicit direction: the title+notes card and the "Fecha límite" chip/calendar reveal carried over unchanged, but "Personalizar" and its color picker are gone from editing entirely — replaced by `Urgente` and `Fijada` switches inlined directly in the sheet (the same switches/copy `taskCustomizeVisible`'s modal used, just relocated). A task's `color` is therefore no longer editable anywhere post-creation; it can still be set once at creation time via `habit-form.tsx`'s own "Personalizar" chip (task creation was not in scope for this change and still works exactly as points 13-14 left it).
    - **The delete-animation fix from point 13/14 (the `withDelay`-on-shrink trick in `onExpandedLayout`) turned out to still not be reliably visible on-device** — that fix only widened the window before the container clipped, it didn't guarantee the fade actually finished inside that window on a real device under real timing. Replaced with a deterministic sequence instead of a race: confirming delete no longer calls `deleteTask` immediately. `(tabs)/index.tsx` sets a `removingTaskId` state and passes `removing={task.id === removingTaskId}` into the affected `TaskCard`; the card's own `useEffect` drives a `withTiming` opacity/scale fade to zero (and disables its `pointerEvents`) over exactly `duration.listItemExit`. Only after a matching `setTimeout` of the same duration does `deleteTask` actually run and remove the task from the store. By the time the array shrinks and `onExpandedLayout`/`extraHeightSV` react to the smaller content, the deleted card has already faded to fully invisible — so there is nothing left for the clip boundary to cut off, regardless of exact timing. The `withDelay` change from point 13/14 was left in place as a harmless second line of defense for any other future shrink case, but it is no longer what makes task deletion look right.
    - **`TaskDetailSheet`'s crooked-looking color dot next to the task title** (the dot sat visibly above the title's baseline) was a `flex-start`-aligned row with a guessed `marginTop` offset that didn't match the `title` text variant's actual line height. Fixed by switching that row to `alignItems: 'center'` and dropping the manual offset — centers the dot, the (possibly multi-line) title, and the close button against each other properly instead of guessing a fixed pixel nudge.
16. **The "+" entry point redesign — deferred since the start of this initiative (see the old "Next up" entry this point replaces) — finally happened, for *creation* only, driven by two Reminderos-style reference mockups the user provided (a compact "New Reminder" floating card, and a "Customise" full sub-sheet).** Both habit creation and task creation moved off `habit-form.tsx`'s big `[0.9]`-detent form sheet onto a new compact floating card. `habit-form.tsx` is now **edit-only**: it no longer reads a `mode` param or renders a segmented control, `useLocalSearchParams` always expects `id`, and every piece of state that only existed for creation (`taskName`, `taskHabitId`, `taskColor`, deadline state, `taskCustomizeVisible`, etc.) was deleted rather than left dormant.
    - **First attempt used a route** (`src/app/create.tsx`, registered with `presentation: 'transparentModal'`) so the screen would paint nothing but a scrim + floating card over whatever was underneath. **Reverted after on-device testing: `transparentModal` did not show the presenting screen behind it at all** — just a flat, empty grey fill, unlike every other overlay in this app. Root cause not fully diagnosed (suspected: this `react-native-screens` version's Android `transparentModal` support not correctly keeping the previous screen composited, an Android-only gap parallel to `formSheet`'s own documented Android limitations in point 1) — not worth chasing further given a proven alternative already existed one line away. **Fixed by abandoning the route entirely**: `CreateSheet` (`features/habits/presentation/components/create-sheet.tsx`) is a plain RN `Modal` component, exactly the pattern `TaskEditSheet`/`TaskDetailSheet`/`ConfirmDialog` already use successfully — the presenting screen is never replaced, so it's still mounted and visible (dimmed by the scrim) behind the Modal by construction, no special-casing needed. 17. **Real bug found on-device: the keyboard fully covered whatever `TextInput` it was editing inside any RN `Modal`-based sheet, on Android.** `AndroidManifest.xml` sets `windowSoftInputMode="adjustResize"` at the Activity level, which is why regular screens/routes (`habit-form.tsx`, Today's search field) already avoided this — the Activity's own window resizes and the OS pushes focused content into view automatically. But React Native's `Modal` component renders as a **separate native Android `Dialog` window**, which does not inherit or participate in the hosting Activity's `adjustResize` — a Modal's content is on its own, and without explicit handling the keyboard simply draws on top of it. `CreateSheet` already had a `KeyboardAvoidingView`, but with `behavior={Platform.OS === 'ios' ? 'padding' : undefined}` — Android's `undefined` behavior meant it did nothing at all. `TaskEditSheet` had no `KeyboardAvoidingView` whatsoever. Fixed both: `behavior={Platform.OS === 'ios' ? 'padding' : 'height'}` (`'padding'` on Android does not reliably work for this case — `'height'` does), wrapping the bottom-anchored card in both sheets, with `flex: 1` on the `KeyboardAvoidingView` itself so `justifyContent: 'flex-end'` has a defined space to align within (a `KeyboardAvoidingView` sized only to its content, without `flex: 1`, can't correctly resolve the card's own `maxHeight: '85%'` against it). `TaskDetailSheet`, `HabitCustomizeSheet`, and `TaskCustomizeSheet` were checked and don't need this — none of them contain a `TextInput`. **Any future `Modal`-based component that adds a `TextInput` must repeat this exact pattern** — it's easy to copy an existing sheet's structure and silently inherit this bug by omitting the `KeyboardAvoidingView` or getting the per-platform `behavior` wrong.

18. **Modals had no close animation anywhere in the app — a real, load-bearing RN gotcha, not a missing polish pass.** Every sheet/dialog (`ConfirmDialog`, `CreateSheet` and its nested pickers, `HabitCustomizeSheet`, `TaskCustomizeSheet`, `TaskEditSheet`, `TaskDetailSheet`, the time picker, `habit-form.tsx`'s reminder-time picker, Today's "..."/"Listas" menus) declared Reanimated `entering`/`exiting` on their children, but RN's `<Modal>` hides its native window **synchronously** the instant `visible` flips to `false` — it never unmounts the JS subtree, so an `exiting` animation never gets a frame to run. Fixed with two new shared primitives in `core/ui/`: `useModalProgress(visible)` (keeps the `Modal` mounted for `duration.default` past a close request while an explicit `withSpring`/`withTiming` progress value drives the scrim/card style — the same "confirm now, mutate the data after the animation window" shape this file already used for task deletion, generalized into a hook) and `useRetainedValue(value)` (for sheets whose visibility is derived from `value !== null`, like `TaskDetailSheet`/`TaskEditSheet` — without it the content vanishes the instant the parent nulls the value, before the close animation the hook just added gets to play). Every modal in the app was rewired onto these. The repeated "centered dialog + `WheelTimePicker`" shape (used by `create-sheet.tsx` ×2, `habit-customize-sheet.tsx`, `task-edit-sheet.tsx`, `habit-form.tsx`) was pulled out into `core/ui/time-picker-modal.tsx` in the process — four copies of the same Modal boilerplate down to one component.

Converted both buttons (and, for the same reason, the checkbox and body-tap) to `GestureTap`. A second, independent bug stacked on top: the edit/delete buttons' wrapping `Animated.View` had `pointerEvents="box-none"`, which on this RNGH version silently breaks touch delivery to a `GestureDetector` nested inside it on Android — removed, since nothing below it needed the box-none passthrough once the buttons themselves became proper nested detectors.
    - **Task creation silently did nothing.** `create-sheet.tsx`'s task branch called `useCases.createTask(...)` directly instead of going through the store (unlike the habit branch, which calls the store's `create` action) — the task really was written to SQLite, but nothing ever called `loadToday()` afterward, so `today` never refreshed and the new task simply never appeared. Added a `createTask` store action (`store.ts`) that wraps the use case and refreshes `today` on success, mirroring `editTask`/`create`.
    - **The "Listas" filter menu lost its own trigger once the filter it applied emptied the list.** The "N pendientes" pill + "Listas" button row was rendered only inside the same conditional branch as the habit list itself, so a filter with zero matches unmounted the row that let you clear the filter — a dead end with no way back except reloading the screen. Restructured so the pill row renders whenever `today.length > 0`, independent of whether the *filtered* result is empty; the empty-filter state now renders its own `EmptyState` below the (still-visible) filter controls. "Listas" also moved into the header icon group next to search/"...", tinted with the accent color while a filter is active — by explicit design feedback, its previous position as a lone floating pill below the header read as misplaced. "Listas" itself went from a placeholder that just reopened the "..." menu to a real filter (Todos / Con tareas pendientes / Completados hoy) over the existing `today` data — no new domain query needed.
20. **A `SuccessOverlay` (`core/ui/success-overlay.tsx`) replaces every remaining "flash a message inside the sheet before it closes" pattern with a full-screen checkmark over a dimmed scrim, shown only *after* the triggering sheet has fully closed — not layered on top of it.** A tiny Zustand store (`useSuccessOverlayStore.show(message, icon?)`) plus one component mounted once in the root `_layout.tsx` (same pattern as `<CreateSheet />` in the tabs layout), visually identical to the existing `DayCompleteOverlay` (badge + title, no card background) rather than a new visual language. `CreateSheet`'s `finishCreate` first went through an in-sheet checkmark-overlay iteration (a `justCreated` state rendered inside the card) — reverted after on-device feedback that the still-visible sheet behind the checkmark read as broken; the fix was sequencing, not styling: call `close()`, wait `duration.default` (the same constant `useModalProgress` uses to actually unmount), *then* call `useSuccessOverlayStore.getState().show(...)`. ## Design system: NativeWind (background — see initiative above for current branch)

Branch `nativewind-obytes`, off `main` (**not** off `expo-sdk-57-upgrade` — that branch's SDK 54→57 bump and its `@expo/ui`/Material 3 Android pilot are `git stash`ed there, untouched, waiting to be resumed separately). This branch is still on the pre-upgrade SDK (`expo` `^54`, `react-native` 0.81.5) — nothing here builds on top of the other branch's work, they're two independent explorations of the same underlying goal (Platform Fidelity: iOS and Android should look native to their own platform, not identical).

Where the two branches diverge on *how* to get platform fidelity: `expo-sdk-57-upgrade` renders actual native SwiftUI/Compose views via `@expo/ui`. This branch instead keeps everything as regular React Native views, styled with **NativeWind** (Tailwind for RN) instead of the hand-rolled `core/theme` token system, and expresses per-platform differences explicitly via `Platform.select()` rather than a different rendering engine per platform. Chosen after `@expo/ui`'s Android bugs (see that branch's `docs/research/expo-ui.md`) cost real time to work around — NativeWind trades "the OS literally draws the control" for "fast, predictable, zero native-bridge bugs," which the user weighed and preferred for how this app should feel day to day.

**Setup:** `tailwind.config.js` (custom `primary`/`neutral`/`danger` palette derived from the app's flame-orange brand, `rounded-3xl` in the radius scale), `global.css`, `babel.config.js` (`babel-preset-expo` with `jsxImportSource: 'nativewind'` *and* the separate `nativewind/babel` preset — both are required, they do different things: the first sets the JSX runtime import, the second is the actual className-to-style transform; not redundant), `metro.config.js` (`withNativeWind`), `nativewind-env.d.ts`. `babel-preset-expo` had to be added as an explicit dependency — it's normally just a transitive/nested dep that a zero-config project never resolves directly, but a custom `babel.config.js` needs it resolvable from the root.

**`src/core/ui-nw/`** is the new component folder, parallel to (not replacing) `src/core/ui/` — Today, Habits, and Habit Detail still run on the original hand-rolled `core/theme` system; only Settings has moved over so far. Contents: `SettingsContainer`, `SettingsItem`, `SegmentedControl`, and `platform-tokens.ts` (centralizes every `Platform.select()` difference in one file instead of scattering them per component — corner radius, icon shape, shadow, and critically **press feedback**: iOS gets `active:opacity-70`, Android gets a *real* native ripple via `Pressable`'s `android_ripple` prop, no `@expo/ui` needed for that).

**Two real bugs found and fixed while building this, not cosmetic tweaks:**
1. NativeWind ships its own theme controller (`colorScheme` from the `nativewind` package) that is **completely independent** from this app's own `useAppearanceStore`. Changing Sistema/Claro/Oscuro updated the Zustand store correctly but NativeWind never found out, so nothing visually changed. Fixed with a `useEffect` in `src/app/_layout.tsx` that bridges `useAppearanceStore`'s scheme into `colorScheme.set()` (imported from `nativewind`) on every change.
2. `habit-form.tsx` felt laggy entering edit mode. It was calling `getHabitDetail` (built for the Habit Detail screen: fetches the *entire* completion history and runs `computeStreaks`/`last30Percent`) just to read a habit's name/icon/color/schedule — none of which needs streaks. Added a lightweight `getHabitUseCase` (`src/features/habits/domain/use-cases/get-habit.ts` → `habits.getById(id)` only, wired into `core/di/composition-root.ts` as `getHabit`), and parallelized it with `getHabitReminder` via `Promise.all` instead of two sequential awaits. Confirmed via a release build (`npm run build:test`) that remaining perceived slowness was normal dev-mode JS overhead, not a further bug.

**Today's swipe-to-edit/delete row** (`draggable-habit-list.tsx`) was also redesigned here: the old solid full-color reveal (an accent/danger block filling the whole action area) is now the app's own `IconWell`-style pattern instead — the row's normal background stays, and a small circular tinted badge shows just the icon in its semantic color. A "flick past the reveal point to commit immediately" gesture (with Apple-design-skill rubber-banding) was built and tested, then **reverted at the user's explicit request** after hands-on testing — it felt unpredictable (an emphatic swipe could fire the action without meaning to). Swipe now only ever reveals the button; tapping it is the only way to trigger edit/delete. Don't re-add auto-commit-on-swipe without asking first — this was a deliberate UX call, not an oversight.

**`scripts/build-android.sh` was always doing a clean prebuild**, on every single local build regardless of variant — wiping `android/.gradle` and `android/app/.cxx` (Gradle/CMake's incremental caches) every time, which is why every native rebuild this session took 10-15 minutes even for trivial changes. Per `ADR-007`, a `--clean` prebuild is only actually required when the `applicationId` changes (switching `dev`/`test`/`prod`). Fixed: the script records the last-built variant in `android/.last-variant` and only forces `--clean` when the variant differs from the last build (or `android/` doesn't exist yet) — same-variant rebuilds now run a plain incremental `prebuild`, so Gradle/CMake's caches survive between builds. (`my-wallet-app`, a sibling project, gets the same speed by keeping `android/` persistent across ordinary `expo run:android` calls — same underlying idea.)

**Settings' cards were restyled to an "elevated surface, no border" look** (reference: dark travel-app UIs where every component gets its own background tint instead of a hairline border) — `SettingsContainer`/`SegmentedControl` dropped the dark-mode border and moved from `bg-neutral-900` to `bg-neutral-800`, and `SettingsItem`'s icon badges switched from a solid-fill circle to a tinted "icon well" (`iconWellClassName`/`iconWellColor` in `platform-tokens.ts`: ~15%-opacity tint of the semantic color behind a solid-color icon). Checking `core/theme/colors.ts` afterwards showed **Today/Habits/Habit Detail already had this exact pattern** — `Card`/`HabitCard` were already borderless with `surface.secondary` (`#1C1C1F` dark) which is the same hex as the new NativeWind `neutral-800`, and `IconWell` already does the tint-background/solid-icon split. Settings had been the outlier, not the other way around. The one genuine gap: those screens' card radius was a flat `radius.lg` (16px) on every platform, while Settings gets a bigger radius on iOS. Fixed by making `radius.lg` itself `Platform.select({ ios: 24, default: 16 })` in `core/theme/spacing.ts` — propagates to every `radius.lg` consumer app-wide, no component changes needed.

**Not yet done on this branch:** Add/Edit Habit's and Habit Detail's screens are still on the original `core/theme` system, not NativeWind — Settings is the only screen migrated so far. iOS hasn't been verified on real hardware for any of this (no Mac/iPhone access currently) — only Android has been confirmed on the physical device.

## Non-negotiable rules

1. **No comments in source code.** Not JSDoc, not `//` explanations. Only functional directives (`eslint-disable`, `@ts-expect-error`). Rationale belongs in `docs/`. If code needs a comment, rename or restructure instead.
2. **UI text in Spanish, code in English.** All user-facing copy lives in `src/core/i18n/strings.ts` — never hardcode a string in a screen.
3. **No design tokens inline.** Colors, spacing, radius, type and motion come from `src/core/theme/`. A raw hex or magic number in a component is a bug. **On `nativewind-obytes`:** NativeWind screens (`core/ui-nw/`) use `tailwind.config.js`'s custom `primary`/`neutral`/`danger` scale instead — the same principle, a different token source. A raw hex/px value inside a `className` string is still a bug there; extend `tailwind.config.js`'s theme instead.
4. **Business logic only in the domain layer.** Components and Zustand stores call use cases; they never contain schedule/streak/validation rules and never touch SQLite.
5. **Docs and code must not drift.** If an implementation decision contradicts `docs/`, update the doc in the same change.

## Architecture

Clean Architecture + Feature-First. Dependencies point inward.

```
src/
  app/                    Expo Router routes (thin, delegate to features)
  core/
    config/               build variant, read from app.config.ts's extra
    theme/                design tokens (colors, typography, spacing, motion) + appearance-store (Zustand)
    ui/                   design-system primitives (hand-rolled, theme-token based — Today/Habits/Habit Detail)
    ui-nw/                NativeWind-styled primitives (this branch's active initiative — Settings only so far)
    i18n/                 all user-facing strings
    domain/               cross-feature use cases + ports (backup, spreadsheet export, delete-all, onboarding, appearance)
    data/                 SQLite connection + migrations + platform adapters
    di/                   composition root
  features/habits/
    domain/               entities, use cases, repository interfaces (pure TS)
    data/                 SQLite repository implementations + mappers
    presentation/         screens' components, Zustand store, formatters
  features/reminders/
    domain/               Reminder entity, use cases, ReminderRepository + NotificationScheduler ports
    data/                 SQLite repository + the expo-notifications adapter
    presentation/         deep-link hook for notification taps
  features/onboarding/
    presentation/         first-launch store (the route guard reads it)
```

- `domain/` imports nothing from React, React Native or SQLite.
- Platform services (notifications) enter the domain as **ports** — an interface in `domain/`, its Expo implementation in `data/`, bound in `core/di`.
- Components never import `data/` directly — everything goes through `core/di`'s `getUseCases()`.
- Streaks are **always derived** from completion history, never stored (FR-4.4).

## Build variants

Three variants, defined by the table at the top of `app.config.ts` and picked with `APP_VARIANT`. Each has its own `applicationId`, so all three install side by side and each gets its own SQLite sandbox. See `docs/decisions/ADR-007.md`.

| Variant | Application ID | Reason to exist |
|---------|----------------|-----------------|
| `dev` | `com.habittracker.app` | Iterating. Debug build, Metro, Fast Refresh. |
| `test` | `com.habittracker.app.test` | QA before publishing. Release APK, no Metro, empty database. |
| `prod` | `com.habittracker` | Publishing. Signed AAB, EAS only. |

- **Switching variants forces a full native rebuild** — the `applicationId` is baked into the generated native project. `scripts/build-android.sh` tracks the last-built variant in `android/.last-variant` and only runs `prebuild --clean` when the variant actually changed (or `android/` doesn't exist yet); rebuilding the *same* variant runs a plain, incremental `prebuild` so Gradle/CMake's caches survive between builds. Budget minutes only when switching variants — same-variant rebuilds should be much faster.
- Application code reads the variant from `src/core/config/` (`appVariant`, `isDev`, `isTest`, `isProd`), never from `process.env`.
- An unknown `APP_VARIANT` throws at config resolution rather than defaulting.

## Verifying on the device

Screenshots and system dumps are how a change gets confirmed here; `tsc` and `eslint` cannot see a Reanimated worklet crash or a notification that never fires.

```bash
adb reverse tcp:8081 tcp:8081      # re-run after EVERY cable reconnect, or the dev client
                                    # hangs on its blue splash and never reaches Metro
adb shell am force-stop com.habittracker.app
adb shell monkey -p com.habittracker.app -c android.intent.category.LAUNCHER 1
adb exec-out screencap -p > shot.png

adb shell dumpsys alarm | grep -A3 habittracker              # is the reminder scheduled? exact or windowed?
adb shell dumpsys notification --noredact | grep habittracker # did it post?
adb shell "run-as com.habittracker.app cat files/SQLite/habit-tracker.db" > local.db  # inspect real rows
```

- Allow ~20-30s after launch before tapping: the dev client has to fetch the bundle first, and taps sent early land on the splash.
- A `ReferenceError: Property 'X' doesn't exist` in the Metro log right after an edit is usually stale Fast Refresh, not a real bug — force-stop and relaunch before chasing it.
- Restore whatever the test touched (completions, archived habits, enabled reminders). The device holds the user's real data.

## Design

The app follows Apple's fluid-interface principles (the `apple-design` skill). Concretely:

- **Springs, not fixed curves,** for anything the user touches. Tokens in `src/core/theme/motion.ts` map to Apple's damping/response model.
- **Press feedback on press-in,** never on release (`PressableScale`).
- **Overshoot only where a gesture carried momentum** — two moments earn it: the completion check, and the day turning complete (`DailyGoal`). Nothing else.
- **Haptics fire on the same frame as the visual.** This is why `toggle` in the store updates optimistically and reconciles afterwards: waiting for the SQLite write put the haptic ahead of the check.
- **Animate `transform` and `opacity` only.** A width/height/margin animation is a bug — `ProgressBar` uses `scaleX` with `transformOrigin: 'left'`, `ColorSwatch` uses `scale`.
- **Never call a plain function inside a worklet.** `useAnimatedStyle` runs on the UI thread; calling a normal helper from it throws `[Worklets] Tried to synchronously call a non-worklet function` at runtime and shows a red screen — with `tsc` and eslint both green. Compute the value on the JS side and let the worklet capture it.
- **Entrance animations use `<Enter>`**, which animates on a screen's **first** focus and renders instantly on every focus after that. Reanimated's `entering` prop only runs on mount, which would skip the animation entirely for a lazily-mounted tab; replaying it on *every* focus was worse — a stagger you see dozens of times a day stops being an entrance and becomes a delay.
- Accent is flame orange — the streak metaphor, and the only warm saturated colour in a neutral palette. The app icon is the same flame; sources live in `assets/brand/` and everything in `assets/images/` is generated from them, never hand-edited. The notification icon is a **second, simpler flame**, because Android flattens it to a 24 dp white silhouette and the launcher mark is illegible at that size (`docs/assets/Brand-Guidelines.md`).
